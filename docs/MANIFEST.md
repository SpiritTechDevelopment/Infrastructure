# Infrastructure manifest

Манифест описывает топологию целиком: какие есть ноды, из каких нод состоит
каждый флот, какие между ними направленные связи. Владелец манифеста —
infrastructure pipeline. Backend его принимает и переносит в свои таблицы.

Из манифеста следует, какие доступы положены каждому customer: нода флота даёт
FREEDOM-доступ, связь — BRIDGE-доступ. Добавили ноду во флот, и всем customer
этого флота выпустились credentials и уехали на неё. Убрали ноду, и доступы
отозвались. Манифест это не опись инвентаря, а команда, меняющая доступ живых
пользователей.

## Формат

Один вызов `ApplyFleetManifest` с манифестом целиком. Ниже минимальный
осмысленный пример: две ноды, один флот, одна связь `NL-1 → DE-1`.

```json
{
  "schema_version": 1,
  "revision": 42,
  "allow_destructive": false,

  "nodes": [
    {
      "node_id": "NL-1",
      "display_name": "Amsterdam",
      "agent": {
        "endpoint": "10.8.0.11:9443",
        "tls_server_name": "nl-1.agent.internal",
        "certificate_identity": "spiffe://spiritvpn/node/NL-1"
      },
      "public": {
        "address": "nl1.example.com",
        "port": 443,
        "reality_public_key": "0rTG1Q...",
        "server_name": "www.microsoft.com",
        "short_id": "6ba85179",
        "fingerprint": "chrome",
        "flow": "xtls-rprx-vision",
        "transport": "tcp"
      }
    },
    {
      "node_id": "DE-1",
      "display_name": "Frankfurt",
      "agent": {
        "endpoint": "10.8.0.12:9443",
        "tls_server_name": "de-1.agent.internal",
        "certificate_identity": "spiffe://spiritvpn/node/DE-1"
      },
      "public": {
        "address": "de1.example.com",
        "port": 443,
        "reality_public_key": "Kx91mA...",
        "server_name": "www.microsoft.com",
        "short_id": "1f4c0a83",
        "fingerprint": "chrome",
        "flow": "xtls-rprx-vision",
        "transport": "tcp"
      }
    }
  ],

  "fleets": [
    {
      "vpn_fleet_id": 1,
      "node_ids": ["NL-1", "DE-1"],
      "bridges": [
        {
          "routing_key": "nl1-de1",
          "entry_node_id": "NL-1",
          "exit_node_id": "DE-1",
          "egress_tag": "out-de1",
          "display_name": "Amsterdam → Frankfurt"
        }
      ]
    }
  ]
}
```

Такой манифест даёт каждому customer флота `1` три доступа: FREEDOM на `NL-1`,
FREEDOM на `DE-1` и BRIDGE `NL-1 → DE-1`.

Вызов идёт по gRPC под mTLS, идентичность вызывающего должна быть в списке
`SPIRIT_ROLE_MANIFEST_WRITER` на стороне backend. Определения сообщений —
`proto/spiritvpn/manifest/v1/manifest.proto`.

## Поля

Все значения принадлежат инфраструктуре, backend ни одно из них не выводит и не
подставляет.

| поле | что это | если ошибиться |
|---|---|---|
| `node_id` | идентичность ноды, назначается один раз навсегда | другое значение означает другую ноду: у customer новые credentials, старые ссылки мертвы |
| `agent.endpoint` | адрес агента в management-сети, `host:port` | backend не дойдёт до агента, команды копятся |
| `agent.tls_server_name` | имя из сертификата агента | рукопожатие backend с агентом не состоится |
| `agent.certificate_identity` | идентичность в сертификате агента | трактуется как подмена ноды, поднимается alert |
| `public.address`, `public.port` | публичная точка входа Xray, куда подключается клиент | ссылка выдастся, клиент не подключится |
| `public.server_name` | домен прикрытия REALITY | ссылка выдастся, клиент не подключится |
| `public.reality_public_key`, `public.fingerprint` | параметры REALITY на ноде | ссылка выдастся, клиент не подключится |
| `public.short_id` | короткий идентификатор REALITY, единственное поле `public`, которое разрешено оставить пустым | уходит в ссылку как `sid=`; пустое значение и отсутствие параметра для клиента означают разное, поэтому параметр не опускается |
| `public.flow`, `public.transport` | зафиксированы в v1: `xtls-rprx-vision` и `tcp` | манифест отклонён |
| `display_name` ноды и связи | человекочитаемое имя, попадает в название профиля у пользователя | косметика |
| `vpn_fleet_id` | идентичность флота, назначается один раз навсегда | чужой номер отдаст customer чужую топологию |
| `routing_key` | идентичность связи внутри флота | другое значение означает другую связь: новое поколение BRIDGE-доступов |
| `egress_tag` | тег outbound в конфиге Xray входной ноды | доступ выпустится, ссылка выдастся, трафик не пойдёт |

Backend проверяет только формальную корректность значений. Соответствие `public.*`
реально поднятому на ноде Xray и соответствие `egress_tag` реально настроенному
outbound он проверить не может: такая ошибка тихая, пользователь получит
нерабочую ссылку.

### tls_server_name и server_name

Два поля с похожими именами относятся к разным соединениям, и путать их дорого.

* `agent.tls_server_name` — соединение backend с агентом в management-сети.
  Значение берётся из сертификата агента, наружу не публикуется. Пример:
  `nl-1.agent.internal`.
* `public.server_name` — соединение клиента с нодой в публичном интернете. Это
  домен прикрытия REALITY: посторонний наблюдатель видит поход на этот сайт.
  Значение должно совпадать с REALITY-конфигом ноды и попадает в VLESS-ссылку
  параметром `sni=`. Пример: `www.microsoft.com`.

Домен прикрытия — чужой сайт, а не ваш. Backend его никак не интерпретирует, он
переносит значение из манифеста в ссылку.

## Порядок работы

1. Собрать манифест из своего инвентаря: **все** ноды и **все** флоты, а не
   только изменившиеся.
2. Взять `revision` больше последней успешно применённой.
3. Выставить `allow_destructive`, если манифест что-то удаляет по сравнению с
   предыдущим.
4. Вызвать `ApplyFleetManifest`.
5. Разобрать ответ: `APPLIED` означает, что манифест принят, `IDEMPOTENT` — что
   он уже был применён и ничего не сделано.

Отказ не оставляет следов: манифест применяется целиком либо не применяется
вовсе. Повторить вызов с теми же номером и содержимым безопасно.

## Проверки

Первая же сработавшая проверка отклоняет манифест целиком.

Формальные, код ответа `InvalidArgument`:

| правило | код ошибки |
|---|---|
| `schema_version` равен 1 | `MANIFEST_SCHEMA_VERSION` |
| `revision` больше нуля | `MANIFEST_REVISION_INVALID` |
| не более 100 нод, 100 флотов, 900 связей суммарно, 10 нод во флоте | `MANIFEST_TOO_LARGE` |
| `node_id`, `vpn_fleet_id`, `routing_key` внутри флота не повторяются | `MANIFEST_DUPLICATE` |
| ссылки на ноды разрешаются в `nodes` того же манифеста | `MANIFEST_UNKNOWN_NODE` |
| поля ноды заполнены и допустимы | `MANIFEST_NODE_INVALID` |
| `egress_tag` непуст, entry и exit различны и оба входят во флот | `MANIFEST_BRIDGE_INVALID` |

Требования к полям ноды: `endpoint` вида `host:port` с портом 1–65535;
`tls_server_name` и `certificate_identity` непусты; `address` непуст, `port`
1–65535; `reality_public_key` и `server_name` непусты; `fingerprint` — ASCII-токен
длиной 1–64 из `[A-Za-z0-9._-]`; `transport` равен `tcp`; `flow` равен
`xtls-rprx-vision`.

Относительно уже принятого состояния, код ответа `FailedPrecondition`:

| правило | код ошибки |
|---|---|
| `revision` больше последней принятой | `MANIFEST_REVISION_REGRESSION` |
| та же `revision` с другим содержимым | `MANIFEST_DIGEST_CONFLICT` |
| каждый принятый ранее флот присутствует | `MANIFEST_FLEET_MISSING` |
| пара `(entry, exit)` у существующего `routing_key` не изменилась | `MANIFEST_BRIDGE_PAIR_IMMUTABLE` |
| удаление разрешено флагом `allow_destructive` | `MANIFEST_DESTRUCTIVE` |

## Свойства, о которых стоит знать заранее

* Манифест всегда полный. Всё, чего в нём нет, считается удалённым; отправить
  дополнение к предыдущему невозможно.
* Принятый `vpn_fleet_id` обязан присутствовать всегда, `allow_destructive` этого
  не отменяет. Пустой флот, без нод и связей, разрешён: это и есть способ
  выключить флот.
* Откат делается вперёд. Чтобы вернуть прежнюю топологию, отправьте прежний
  манифест под новой большей `revision`. Digest считается от содержимого без
  учёта номера, поэтому backend распознает такое как штатную операцию.
* `allow_destructive` действует на один вызов и на следующие не переносится. Флаг
  защищает от усечённого манифеста: сгенерированный с ошибкой и потерявший
  половину нод не пройдёт молча.
* Нода, исчезнувшая и вернувшаяся под тем же `node_id`, получает новое поколение
  доступов: новые `client_uuid`, старые ссылки мертвы.

## Если нода не отвечает

Недоступность ноды не влияет ни на приём манифеста, ни на состав флота.
`ApplyFleetManifest` не обращается к агентам вообще, он пишет только в
PostgreSQL, поэтому манифест с десятком мёртвых нод применится как обычный.

| что | поведение |
|---|---|
| команды агенту | копятся в очереди, повторяются с растущей паузой от 1 секунды до 5 минут, без предела попыток |
| трафик | не забирается; агент копит его у себя и отдаст, когда связь вернётся |
| квота | до тех пор не тратится: пользователь может выйти за лимит, списание произойдёт разом при возврате ноды |
| сверка состава | не выполняется, расхождение на ноде не обнаруживается |
| доступ пользователей | продолжает работать: Xray на ноде живёт своей жизнью, backend для соединения клиента не нужен |
| ссылки | выдаются как обычно, `GetCustomerAccessLinks` до нод не ходит |

Вмешательства это не требует. Вернувшаяся нода получит накопленные команды,
отдаст накопленный трафик и пройдёт сверку.

Повторы сами не прекращаются. Команда становится окончательно провальной только
на ответах вида «неверный аргумент», «доступ запрещён», «метод не реализован»:
это признаки несовместимости или неверной конфигурации, но не недоступности.

## Вывод ноды из эксплуатации

Убрать ноду из флота и убрать её из манифеста целиком — разные операции с разными
последствиями.

Если убрать ноду из `node_ids` флота, оставив в `nodes`, доступы customer
отзываются и backend выпускает агенту `EnsureUserAbsent` на каждого. Пользователи
будут вычищены из Xray сразу либо позже, когда нода вернётся.

Если убрать ноду из `nodes`, доступы тоже отзываются, но команды агенту **не
выпускаются**. Слать их некуда: endpoint'а больше нет в манифесте, ожидающие
команды переводятся в `SUPERSEDED`. Backend считает работу завершённой, а
пользователи остаются заведёнными в Xray на той машине.

Отсюда порядок:

1. Убрать ноду из `node_ids` всех флотов, оставив в `nodes`. Манифест с
   `allow_destructive: true`.
2. Дождаться, пока команды удаления доедут до агента.
3. Убрать ноду из `nodes` следующим манифестом.
4. Погасить машину.

Шаг 3 без шага 2 оставит на машине работающих пользователей: backend перестанет
считать себя ответственным за ноду, а Xray продолжит их принимать, пока машину не
выключат физически. Вычистить их backend уже не поможет.

## Что произойдёт при типичных изменениях

| изменение | последствие |
|---|---|
| добавлена нода во флот | всем customer флота выпускается FREEDOM-доступ, агенту уходит команда завести пользователя |
| добавлена связь | всем customer флота выпускается BRIDGE-доступ на входной ноде |
| нода убрана из флота, но осталась в `nodes` | доступы отзываются, агенту уходит команда удалить пользователей |
| нода убрана из `nodes` | доступы отзываются, команды агенту не выпускаются |
| нода вернулась под тем же `node_id` | новое поколение доступов, новые `client_uuid`, старые ссылки мертвы |
| изменился `public.*` ноды | ссылки собираются по-новому при следующем запросе, credentials сохраняются |
| изменился `agent.endpoint` | backend начинает ходить на новый адрес, доступы не затронуты |
| изменился `egress_tag` связи | новое значение уезжает агенту, credentials и поколение сохраняются |
| у существующего `routing_key` изменилась пара entry/exit | манифест отклоняется, нужен новый `routing_key` |
| флот опустел, но остался | все доступы его customer отзываются, сам флот сохраняется |
