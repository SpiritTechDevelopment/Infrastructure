# Контракт бэкенда

Нормативная доменная модель центрального бэкенда SpiritVPN. Этот репозиторий её
**не владеет** — он её потребляет и обязан ей соответствовать.

| Файл | Что это |
|---|---|
| [BACKEND_DOMAIN_AGREEMENTS.md](BACKEND_DOMAIN_AGREEMENTS.md) | Единственный источник истины о доменной модели и границах бэкенда |

## Происхождение

```text
репозиторий  git@github.com:SpiritTechDevelopment/SpiritVPN.git
файл         dev/BACKEND_DOMAIN_AGREEMENTS.md
коммит       8f69f2532de642e31658f13b198e4775d89c694c
дата         2026-08-07
```

Копия вендорена, а не подключена по относительному пути, по двум причинам:
CI не имеет доступа к соседнему рабочему каталогу, и зафиксированный SHA даёт
воспроизводимость — понятно, против какой именно редакции проверялись схемы.

## Обновление

Правки вносятся **в репозитории-источнике**. Сюда изменение подтягивается целиком:

```sh
scripts/vendor-backend-contract.sh <commit-sha>
```

После обновления обязательно перепроверить:

1. инварианты компилятора в `fleetctl` (лимиты, правила валидации манифеста);
2. схемы в `contracts/desired-state/` и `contracts/schemas/`;
3. открытые решения в
   [`INFRA_TECHNICAL_SPEC.md` §23](../../docs/architecture/INFRA_TECHNICAL_SPEC.md#23-открытые-решения);
4. дельту к бэкенду в
   [`INFRA_TECHNICAL_SPEC.md` §24](../../docs/architecture/INFRA_TECHNICAL_SPEC.md#24-дельта-к-бэкенду).

Единственное локальное отличие вендоренного файла от источника — врезка о
происхождении в первых восьми строках. Проверить, что остальное совпадает:

```sh
diff <(tail -n +9 contracts/backend/BACKEND_DOMAIN_AGREEMENTS.md) \
     <(git -C ../SpiritVPN show 8f69f253:dev/BACKEND_DOMAIN_AGREEMENTS.md)
```

## Что этот документ определяет, а что нет

Определяет: клиентский доступ, `client_uuid` и accounting ID, квоты и учёт,
логическую схему infrastructure manifest и правила его валидации, семантику
agent operations, модель PostgreSQL, лимиты масштабирования.

Не определяет (это зона данного репозитория): топологию, состав флотов,
нейминг Xray-сущностей, включая `egress_tag`, порядок раскатки, DNS,
инфраструктурные credentials BRIDGE → EXIT.

Расхождения между этим документом и реализацией устраняются согласованно
**до** merge или deploy, а не постфактум.
