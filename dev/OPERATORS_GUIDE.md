# Операторский доступ: включение, работа, отзыв

Этот документ описывает жизненный цикл оператора целиком: как человек получает
доступ к инфраструктуре, как этим доступом пользуются и как его отбирают.

Он самодостаточен — читать его подряд можно, ничего не зная о репозитории. Всё
остальное (редактирование желаемого состояния, выкатки, Vault, диагностика)
живёт в [руководстве оператора](../docs/operations/INFRA_V1_GUIDE_RU.md), и
здесь оно не пересказывается.

Кому что читать:

- **новому оператору** — [часть A](#часть-a-получение-доступа);
- **тому, кто выдаёт доступ** — [часть B](#часть-b-выдача-доступа);
- **при уходе человека** — [часть C](#часть-c-отзыв-доступа).

---

## Модель доступа в двух словах

Три утверждения, из которых следует всё остальное.

**Инфраструктура не имеет публичной управляющей поверхности.** У управляющего
сервера и у нод нет открытых наружу портов управления. Всё администрирование
идёт через частную сеть WireGuard — управляющий оверлей. Не попав в него, нельзя
ни подключиться по SSH, ни открыть Grafana, ни увидеть Vault.

**Приватные ключи никогда не передаются.** Оператор создаёт их сам на своей
машине. Наружу уходят только публичные части, и именно они попадают в Git. Ни
один приватный ключ не существует нигде, кроме машины владельца.

**Доступ — это отревьюенное изменение в Git, а не действие на сервере.** Выдача
и отзыв правят объявления, проходят pull request и применяются отдельной
защищённой операцией. Поэтому доступ можно посмотреть в истории и отобрать
обратным изменением.

### Почему не «прислать архив с ключами»

Такой способ выглядит проще, и он неверен по трём причинам сразу.

Зашифровать набор *для нового оператора* нечем: ключа у него ещё нет — иначе
архив не понадобился бы. Остаётся общая парольная фраза, и вся безопасность
выдачи сводится к ней.

Шифротекст в Git остаётся **навсегда**. Его можно подбирать офлайн, без
ограничения скорости и без срока давности. Удалить из истории нельзя.

Ключами владели бы двое. После этого журнал не может связать действие с
человеком, а отзыв превращается из правки одной строки в ротацию всего, что
архив мог открыть.

## Часть A. Получение доступа

### A1. Что нужно на машине

Git, Python 3, Make, `sops`, `age`, `ssh-keygen` и инструменты WireGuard
(`wg`, `wg-quick`). Дальше — клон репозитория.

### A2. Создать личность

```bash
make operator-identity OPERATOR="ваш-идентификатор"
```

Идентификатор — строчные латинские буквы, цифры и дефис; он же станет именем
вашего peer в оверлее.

Команда создаёт три пары ключей и кладёт приватные части в
`~/.config/spiritvpn` с правами `0600`:

| Ключ | Для чего |
|---|---|
| age | расшифровка желаемого состояния и контракта платформы |
| SSH | вход на управляющий сервер |
| WireGuard | членство в управляющем оверлее |

Рядом появляется файл запроса на включение. В нём **только публичные части** —
его можно передать любым каналом, важна целостность, а не секретность.

Повторный запуск не перезапишет существующие ключи: перезапись отняла бы доступ
у уже включённой личности, а восстановить его было бы нечем.

### A3. Передать запрос и сверить отпечаток

Команда напечатала **отпечаток включения** — одну строку вида
`923f ce0d b760 ...`. Она покрывает все три ключа сразу.

Отправьте файл запроса выдающему оператору и **прочитайте ему отпечаток голосом
или лично**. Это единственный якорь доверия во всей процедуре. Канал передачи
файла может быть каким угодно, потому что подмена файла изменит отпечаток, и
сверка её поймает. Без сверки выдающий оператор включит того, кто перехватил
запрос, — и узнает об этом не скоро.

Не отправляйте отпечаток тем же каналом, что и файл.

### A4. Дождаться слияния и применения

Выдающий оператор откроет pull request, получит ревью и применит изменение. До
этого момента ничего из следующего не заработает.

### A5. Подключиться к оверлею

Заберите `main` и прочитайте контракт: в нём публичный ключ управляющего
сервера, его внешний эндпоинт, сети оверлея и выданный вам адрес.

```bash
git pull --ff-only origin main
sops --decrypt inventories/bootstrap/platform.sops.yml | less
```

Соберите конфигурацию WireGuard локально. Приватный ключ у вас уже есть после
шага A2; остальное берётся из контракта.

```ini
[Interface]
PrivateKey = <содержимое ~/.config/spiritvpn/keys/operator-wg.key>
Address    = <выданный вам адрес>/32

[Peer]
PublicKey           = <публичный ключ управляющего сервера>
Endpoint            = <внешний эндпоинт управляющего сервера>
AllowedIPs          = <сети оверлея из контракта>
PersistentKeepalive = 25
```

Не сохраняйте расшифрованный контракт на диск и не переносите значения из чужих
примеров.

Поднимите туннель штатным способом системы (`wg-quick up`) и проверьте
связность по оверлейному адресу управляющего сервера:

```bash
ping -c1 "оверлейный-адрес-управляющего-сервера"
```

Echo внутри оверлея разрешён намеренно — это единственное место, где он
работает. Наружу узлы не отвечают на ping и сами не пингуют: молчание публичного
адреса не является признаком поломки.

### A6. Внутренние имена

```bash
make operator-hosts | sudo tee -a /etc/hosts
```

Именно `sudo tee`, а не `sudo make ... >> /etc/hosts`: перенаправление выполняет
оболочка от вашего имени, а `/etc/hosts` принадлежит root, поэтому второй вариант
падает с «Permission denied» ещё до запуска команды.

Одна строка, вставляется один раз. Имена живут под `.internal`: этот суффикс
зарезервирован ICANN под частное использование и никогда не станет настоящим
доменом. Произвольный TLD такой гарантии не даёт — если его однажды делегируют,
запрос, ушедший мимо туннеля, ответит кто-то посторонний.

Отдельной службы DNS в контуре нет намеренно: ради двух имён это был бы ещё один
компонент и ещё одна поверхность на машине, которая держит Vault.

### A7. Что доступно

| Через что | Что именно |
|---|---|
| SSH на управляющий сервер | операторские действия, локальные SSH-туннели |
| `https://vault.management.internal:8200` | Vault UI |
| `http://grafana.management.internal:3000` | Grafana |
| Локальный SSH-туннель | Prometheus, Alertmanager, Loki — слушают только петлю |

**Порт обязателен.** Ни один из интерфейсов не слушает 80 или 443, поэтому
`http://grafana.management.internal/` без порта не откроется. Точные адреса
печатает `make operator-hosts` — она читает их из контракта, и при расхождении
права она, а не эта таблица.

Grafana и Vault открыты **только операторским адресам**. Firewall управляющего
сервера не доверяет оверлею целиком, поэтому нода флота до них не дотягивается —
это важно, потому что ноды стоят в интернете.

Grafana требует входа: анонимный доступ выключен намеренно. Внутри туннеля она
работает по HTTP — WireGuard шифрует участок оператор—сервер, и другие участники
оверлея этот трафик не видят.

Vault отдаёт TLS, подписанный локальным CA управляющего сервера. Его сертификат
нужно один раз добавить в доверенные, а обращаться — по имени: оверлейного
адреса в SAN сертификата нет.

### A8. Чего доступ не даёт

**Прав внутри Vault.** Политика Vault этими командами не выдаётся вовсе. Видеть
UI и иметь права на секреты — разные вещи; второе оформляется отдельно, см.
раздел «Vault» в [руководстве оператора](../docs/operations/INFRA_V1_GUIDE_RU.md).

**Права применять изменения молча.** Контракт доступа к платформе намеренно не
проходит через обычную выкатку.

## Часть B. Выдача доступа

Выполняет действующий оператор, у которого уже есть доступ.

### B1. Сверить отпечаток — сначала

Получив файл запроса, посчитайте отпечаток и **сверьте его с человеком по
другому каналу**: голосом, видео, лично.

Это не формальность и не последний шаг проверки — это единственное, что
отличает включение коллеги от включения того, кто перехватил переписку. Файл
запроса публичен и подменяем; отпечаток покрывает все три ключа, поэтому любая
подмена его меняет.

### B2. Выбрать адрес в оверлее

Адрес задаётся явно и обязателен. Автоматический выбор здесь был бы опасен:
адреса нод флота живут в отдельных фрагментах конфигурации, а не в контракте
платформы, поэтому инструмент их не видит и мог бы молча выдать занятый адрес —
и сломать маршрутизацию оверлея.

Берите адрес из диапазона, отведённого операторам. Занятые операторские адреса
видны в контракте; адреса нод — в скомпилированных планах.

### B3. Внести в объявления

```bash
make operator-grant REQUEST="файл-запроса" ADDRESS="адрес"
```

Команда спросит подтверждение сверки, затем добавит:

- SSH-ключ — в операторский ростер контракта платформы;
- peer WireGuard — с выданным адресом;
- age-получателя — в `.sops.yaml`,

и перешифрует все затронутые файлы. После этого она **останавливается**: ничего
не применено, в рабочем дереве лежит diff.

### B4. Ревью и применение

```bash
make check      # конверты и набор получателей
git diff        # прочитать изменение
```

Дальше коммит, pull request, ревью по CODEOWNERS. Применяется изменение
защищённой операцией — см. раздел «Первичная настройка и защищённое обновление
платформы» в [руководстве оператора](../docs/operations/INFRA_V1_GUIDE_RU.md).

Обычная выкатка платформы такое изменение не пропустит: исполнитель сравнивает
Git с явно применённым контрактом доступа и останавливается.

### B5. Сообщить новому оператору

После применения — сказать, что можно выполнять шаги A5–A6. Адрес он увидит в
контракте сам.

## Часть C. Отзыв доступа

### C1. Отозвать

```bash
make operator-revoke OPERATOR="идентификатор" AGE_RECIPIENT="age1..."
```

`AGE_RECIPIENT` обязателен, и это не формальность. Удаление из ростера закрывает
SSH и оверлей, но **не отнимает возможность расшифровывать**: пока получатель
остаётся в `.sops.yaml`, бывший оператор продолжает читать всё желаемое
состояние из любой копии репозитория. Этот отказ ничего не ломает видимо и
длится сколько угодно, поэтому команда без получателя отзыв не выполняет.

Получателя возьмите из `.sops.yaml` или из исходного запроса на включение.

Отозвать последнего оператора нельзя: доступ к платформе был бы утрачен целиком.

### C2. Применить

Тот же путь, что и при выдаче: `make check`, ревью, защищённое применение.
**Пока изменение не применено, отзыв не состоялся** — старый SSH-ключ и peer
продолжают работать.

### C3. Что отзыв не делает

**Не стирает ключи с машины ушедшего.** Они остаются у него; бесполезными их
делает то, что сервер их больше не принимает.

**Не отзывает прав в Vault.** Это отдельная операция, и её нужно выполнить.

**Не меняет общие секреты.** Если человек знал пароль администратора Grafana,
пароли учётных записей или значения секретов из Vault — знание осталось при нём.
Отзыв доступа и ротация секретов, которые он видел, — две разные задачи, и вторая
обычно нужнее.

## Как устроен оверлей

Управляющий сервер — центр звезды: с ним соединяются и операторы, и ноды флота,
и выделенный раннер. Прямых соединений между участниками нет — весь транзит идёт
через сервер.

Кто что инициирует:

- **нода → сервер**: поднимает туннель сама и шлёт логи. Входящего слушателя
  WireGuard у ноды нет вовсе, её порт наружу закрыт;
- **сервер → нода**: управление агентом, сбор метрик, готовность;
- **оператор → сервер**: SSH, Grafana, Vault;
- **оператор → нода**: транзитом через сервер.

Что открыто на управляющем сервере со стороны оверлея:

| Порт | Кому |
|---|---|
| SSH | операторам и раннеру |
| Grafana, Vault | только операторам |
| приём логов | всем нодам |

Это единственный порт, открытый всему оверлею, и открыт он на запись, а не на
чтение. Всё остальное — Prometheus, Alertmanager, Loki на чтение, экспортёр
хоста — слушает только петлю сервера и достаётся SSH-туннелем.

Раньше firewall доверял оверлейному интерфейсу целиком, и тогда любой узел
дотягивался до всего, что слушает оверлейный адрес. Сейчас вход объявлен
поимённо, а список источников выводится из ростера — поэтому включение оператора
автоматически открывает ему Grafana и Vault, и отдельного списка, который можно
забыть обновить, не существует.

## Если что-то не работает

**`sops` не расшифровывает.** Изменение ещё не применено, либо `SOPS_AGE_KEY_FILE`
не указывает на вашу личность. Проверьте, что ваш получатель есть в `.sops.yaml`
на текущем `main`.

**Туннель поднялся, но сервер не отвечает.** Сверьте выданный адрес и
`AllowedIPs` с контрактом. Проверьте, что `Endpoint` — внешний адрес сервера, а
не оверлейный.

**SSH просит пароль или отвергает ключ.** Ростер применяется защищённой
операцией; если она не выполнена, ключа на сервере ещё нет.

**`ERR_EMPTY_RESPONSE` или пустой ответ от Grafana.** Открыт адрес без порта.
Ни Grafana, ни Vault не слушают 80 и 443 — нужен `:3000` и `:8200`
соответственно.

**Grafana или Vault не открываются, а SSH работает.** Проверьте по порядку:

```bash
getent hosts grafana.management.internal        # строка в /etc/hosts на месте?
ping -c1 "оверлейный-адрес-управляющего-сервера" # туннель поднят?
curl -sS -o /dev/null -w '%{http_code}\n' http://grafana.management.internal:3000/login
```

Отказ в соединении означает, что ваш адрес не попал в правило firewall — то есть
выдача применена не полностью. Таймаут означает, что туннель не поднят. Ответ
`200` или `302` — интерфейс работает, дело в браузере.

Vault по адресу и не должен открываться: в SAN сертификата этого адреса нет,
обращаться нужно по имени.

**Ноды не отвечают на ping по публичному адресу.** Так и задумано.

## Правила

- Приватные ключи не покидают машину владельца — ни в Git, ни в мессенджер, ни
  в архив.
- Отпечаток включения сверяется вне того канала, которым передан запрос.
- Расшифрованный контракт не сохраняется на диск.
- Идентичность оператора не копируется на раннер, идентичность раннера не
  используется на ноутбуке.
- Отзыв не считается выполненным, пока изменение не применено.
- Уход человека, знавшего общие секреты, требует их ротации отдельно от отзыва
  доступа.
