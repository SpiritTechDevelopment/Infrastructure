# Инфраструктура SpiritVPN

Этот репозиторий — основной источник желаемого состояния инфраструктуры
SpiritVPN и кода, который приводит серверы к этому состоянию. Изменения идут
в направлении **Git → управляющая платформа → серверы**. Фактическое состояние
серверов используется только для проверок готовности и отчётов о расхождениях; оно не
записывается обратно в Git как новое желаемое состояние.

Актуальная пошаговая инструкция находится в
[руководстве оператора](docs/operations/INFRA_V1_GUIDE_RU.md). Нормативной
архитектурной спецификации в репозитории нет намеренно: документ, разошедшийся
с кодом, источником истины не является, поэтому устаревшая спецификация и
снимок состояния реализации сняты с `main` и остались в истории Git. Устройство
работающей системы описывают `desired/`, `contracts/`, `fleetctl/`, `roles/` и
это руководство.

Для отказа управляющего сервера, аномальной загрузки ресурсов или неизвестного
Linux-сервиса используйте раздел
[«Аварийное расследование управляющего сервера»](docs/operations/INFRA_V1_GUIDE_RU.md#21-аварийное-расследование-управляющего-сервера):
он отделяет read-only сбор доказательств от согласованного сдерживания.

## Текущее состояние

На текущем `main`:

- управляющая платформа развёрнута и описана SOPS-контрактом;
- Vault, управляющий WireGuard, защищённые исполнители и выделенный раннер
  участвуют в рабочем контуре развёртывания;
- `develop` содержит управляющий контур, Telegram-бот и VPN-флот из одной
  входной и одной выходной ноды;
- образы компонентов закреплены по digest;
- Prometheus, Alertmanager, Grafana, Loki, Alloy и exporters разворачиваются из
  Git и получают цели из скомпилированного желаемого состояния;
- успешный CI точного коммита `main` запускает сверку `develop` в порядке
  platform → control → fleet;
- манифест backend отправляется по mTLS, а успешная выкладка флота двигает
  `refs/deployments/develop` отдельной операцией compare-and-swap;
- `prod` содержит только объект окружения и не применяется автоматически.

Первичная установка, ротация доступа, опасные операции, инициализация Vault и
выкладка `prod` остаются явными операторскими действиями.

## Как работает GitOps-контур

```text
изменение в Git
      │
      ▼
CI: SOPS-конверт, схемы, тесты, lint, детерминированная компиляция
      │
      ▼
доверенный CI: расшифровка и проверка реального желаемого состояния
      │
      ▼
desired-state-deploy для точного SHA текущего main
      │
      ├── platform-deploy ── управляющий сервер, Vault, исполнители, мониторинг
      ├── control-deploy  ── PostgreSQL, backend, бот, цели мониторинга
      └── fleet-deploy    ── входные/выходные ноды, Xray, NodeAgent, готовность
                                │
                                ▼
                     манифест backend + Git-ссылка развёртывания
```

Процесс GitHub Actions не выбирает «последний доступный» коммит. Он получает
полный SHA, проверяет его достижимость из `main`, передаёт на управляющий сервер
точный Git bundle и применяет только этот снимок. Если проверенный SHA уже не является
текущим `main`, автоматическая выкатка останавливается.

База сравнения — головной коммит прошлой успешной сверки, а не родитель
головного коммита. Поэтому push из нескольких коммитов разбирается целиком, а
дельта сверки, остановленной красным прогоном, доезжает следующей. Когда
успешной сверки в истории нет, сравнение идёт с пустым деревом и сверяются все
контуры: догадка о базе стоила бы тихого недовыката.

Для `develop` сверка запускается после успешного CI. `prod` намеренно
отфильтрован из автоматического пути: его можно применять только ручным
запуском точного SHA.

## Где хранится состояние

| Объект | Владелец |
|---|---|
| Топология `develop` и `prod` | `desired/environments/*/topology.sops.yml` |
| Общие версии, сеть, лимиты, Xray и observability | `desired/common/*.yml`, зашифровано SOPS |
| Стабильные идентификаторы флотов | `desired/fleet-ids.yml`, зашифровано SOPS |
| Первичная настройка управления, доступ и контракт раннера | `inventories/bootstrap/platform.sops.yml` |
| Схемы, компилятор, роли, playbooks и workflows | Git |
| Runtime-секреты сред | Vault; в Git находятся только ссылки `secret://` |
| Входные данные первичной настройки и доступа | SOPS-контракт платформы |
| Закрытые ключи машин и локальные TLS-ключи | Только соответствующий сервер |
| Применённая fleet-база | `refs/deployments/<environment>` |
| Ревизии манифеста и состояние продолжения | `/var/lib/spiritvpn/fleetctl` на управляющем сервере |
| Данные Vault | Raft-хранилище Vault и внешние зашифрованные снимки |

`build/`, расшифрованные YAML, временные Ansible vars и планы раннера являются
производными артефактами. Их нельзя коммитить или прикладывать к workflow.

## Структура репозитория

| Путь | Назначение |
|---|---|
| `desired/` | Зашифрованное желаемое состояние сред и общих компонентов |
| `contracts/` | JSON Schema и сетевые контракты |
| `fleetctl/` | Валидация, компиляция, план влияния и координатор развёртывания |
| `inventories/bootstrap/` | SOPS-контракт управляющей платформы и раннера |
| `playbooks/` | Platform, control, bootstrap, configure и readiness playbooks |
| `roles/` | Идемпотентная реализация конфигурации компонентов |
| `scripts/` | Ограниченные операторские и CI-точки входа |
| `.github/workflows/` | Процессы CI, выпуска и развёртывания |
| `tests/` | Модульные тесты и синтетические fixtures без действующих секретов |
| `docs/operations/INFRA_V1_GUIDE_RU.md` | Актуальное руководство оператора |

Ansible хранит механизм настройки, а `desired/` — конкретное желаемое
состояние. Переносить шаблоны, задачи systemd или реализацию firewall в
`desired/` не нужно: оба слоя уже версионируются в Git, но отвечают за разные
вещи.

## Локальная подготовка

Нужны Git, Python 3, Make, SOPS, age, WireGuard tools и Ansible Core 2.18.

```bash
python3 -m venv ansible-env
ansible-env/bin/pip install -r requirements-ansible.txt
export PATH="$PWD/ansible-env/bin:$PATH"
export ANSIBLE_LOCAL_TEMP=/tmp/spiritvpn-ansible-local
```

Основная локальная проверка:

```bash
make ANSIBLE_VENV=./ansible-env check
make lint
```

Проверка SOPS-контракта платформы:

```bash
python3 scripts/platform-sops.py check \
  --bundle inventories/bootstrap/platform.sops.yml
```

Публичный GitHub runner проверяет только корректность SOPS-конвертов и
синтетические fixtures. Реальное желаемое состояние расшифровывает только
доверенный выделенный раннер с локальной age identity.

## Обычный путь изменения

1. Обновить локальную ветку от `origin/main`.
2. Открыть нужный SOPS-файл командой `sops FILE`.
3. Изменить только желаемое состояние; не копировать туда обнаруженное состояние сервера.
4. Запустить локальные проверки.
5. Сделать коммит и отправить его на проверку либо в согласованный процесс `main`.
6. Дождаться CI и автоматической сверки `develop`.
7. Проверить готовность, метрики, логи и Git-ссылку развёртывания.

Процессы выпуска backend, agent и bot изменяют только закреплённые digest
образов внутри SOPS topology. Выпуск develop попадает в `main` автоматически;
выпуск prod создаёт pull request.

## Особая граница доступа к управляющей платформе

Изменение `inventories/bootstrap/platform.sops.yml`, влияющее на SSH,
WireGuard, peers раннера или другой контракт доступа, нельзя протолкнуть обычным
`platform-deploy`: исполнитель сравнивает Git с явно применённым контрактом и
останавливается fail-closed.

После проверки и коммита оператор применяет такой контракт через существующий
управляющий туннель:

```bash
scripts/platform-bootstrap.sh --reuse-tunnel --apply
```

Только после успешного защищённого обновления обычный `platform-deploy` снова
может сверять постоянное состояние. `/etc/spiritvpn/platform/runtime-vars.yml`
— запись явно принятой границы доступа, а не второй источник желаемого состояния.

## Ограничения текущего контура

Репозиторий уже управляет рабочим `develop`, но до полностью непрерывного
GitOps остаются известные границы:

- VPS создаются и удаляются у провайдера вручную;
- сверка DNS запускается отдельно и не удаляет записи автоматически;
- нет периодической полной сверки всех нод флота при отсутствии Git diff;
- жизненный цикл динамических WireGuard peer-фрагментов нод ещё не полностью
  выражен как Git-owned набор;
- обновление сертификатов нод пока только создаёт локальный marker;
- снимки Vault, состояние CA и `/var/lib/spiritvpn/fleetctl` требуют внешнего
  резервного копирования и проверенной процедуры восстановления;
- готовность не проверяет ноду снаружи: адаптеры smoke-проверок задаются на
  управляющем сервере и в Git не описаны, а скомпилированные внешние пробы
  публичного порта никем не читаются — ни один автоматический механизм не
  подтверждает достижимость ноды из интернета;
- маскировочный сайт REALITY одинаков на всех нодах, поэтому опознание одной
  ноды опознаёт весь флот;
- опасные изменения флота и `prod` не применяются автоматически.

Эти ограничения нельзя обходить ручными правками серверов. До появления
соответствующего механизма сверки изменения выполняются отдельной операторской
процедурой и фиксируются в Git там, где они являются желаемым состоянием.

## Основные правила безопасности

- Не коммитить открытые IP, домены, порты, сертификаты, токены или ключи.
- Не передавать закрытые ключи и учётные данные Vault в артефакты или логи GitHub.
- Не использовать `ssh-keyscan` как источник доверия к новому серверу.
- Не применять SHA, который не является проверенным коммитом из `main`.
- Не включать `initial`, `resume` или `allow_destructive` без понимания причины.
- Не двигать Git-ссылку развёртывания, пока backend не подтвердил манифест.
- Не превращать обнаруженное состояние сервера в желаемое состояние автоматически.
- Не изменять сервер вручную, если та же настройка должна принадлежать Git.
- Не проверять доступность узлов пингом по публичному адресу: echo разрешён
  только внутри управляющего оверлея и наружу не отвечает.
